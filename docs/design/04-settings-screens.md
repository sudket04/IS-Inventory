## 1. ทำไมต้องออกแบบใหม่

หน้า Administration เดิมออกแบบไว้ตอนระบบมี 25 ตาราง ใช้โครงสร้างแท็บ 3 ระดับ

```
Administration
├── Users
├── Master Data   → Locations │ Departments │ Vendors │ Manufacturers │ Categories
└── Settings      → Email │ Notifications │ System
```

ปัจจุบันระบบมี 66 ตาราง และจุดที่ต้องตั้งค่าเพิ่มจาก **9 เป็น 24 รายการ**

| ปัญหาของโครงสร้างเดิม | ผลที่เกิด |
|---|---|
| แท็บแนวนอนรับได้ราว 6–7 รายการ | 24 รายการจะล้นจนต้องเลื่อนแนวนอน |
| แท็บไม่บอกลำดับชั้น | ผู้ใช้ไม่รู้ว่า "โซนเครือข่าย" กับ "ชั้นความลับ" ต่างกลุ่มกัน |
| ไม่มีที่แสดงสถานะ | Sync ล้มเหลว 3 วันแล้วไม่มีใครเห็นจนกว่าจะเข้าไปดูเอง |
| หาไม่เจอ | ไม่มีช่องค้นหา ต้องเดาว่าอยู่แท็บไหน |

**จึงเปลี่ยนเป็นแถบเมนูด้านซ้ายแบบจัดกลุ่ม** ซึ่งรองรับได้ถึงหลักร้อยรายการโดยยังหาเจอ

## 4. รูปแบบร่วม — ตารางข้อมูลหลัก

จาก 24 หน้า มี **12 หน้าที่โครงสร้างเหมือนกันทุกประการ** ได้แก่ แผนก · หมวดหมู่ · ผู้ผลิต ·
ผู้ขาย · สถานะทรัพย์สิน · บทบาท Server · ประเภทความสัมพันธ์ · โซนเครือข่าย · ชั้นความลับ ·
ระดับสิทธิ์ · หมวดหมู่เว็บไซต์ · รุ่นอุปกรณ์

**ไม่ควรเขียนแยก 12 หน้า** ให้สร้างส่วนประกอบเดียวที่กำหนดพฤติกรรมด้วยข้อมูลตั้งค่า

```

│  ตั้งค่าระบบ › องค์กร › แผนก                                                   │
│  ──────────────────────────────────────────────────────────────────────────  │
│  แผนก (12)                     [🔍 ค้นหา...    ] [▾ ทั้งหมด] [ + เพิ่มแผนก ]  │
│                                                                              │
```

### 4.1 ข้อมูลตั้งค่าของแต่ละหน้า

```ts
{
  entity:       'departments',
  titleTh:      'แผนก',
  icon:         'Building2',
  columns:      [
    { key: 'code',      label: 'รหัส',      width: 80 },
    { key: 'name',      label: 'ชื่อแผนก',   grow: true },
  ],
  usageCounts:  [                       // นับการอ้างอิงเพื่อคุมการลบ
    { table: 'assets',      label: 'ทรัพย์สิน' },
    { table: 'file_shares', label: 'โฟลเดอร์'  },
  ],
  softDelete:   'is_active',
  permission:   'settings.organization.manage',
}
```

**ผลที่ได้** — เขียนส่วนประกอบเดียวประมาณ 400 บรรทัด แทนการเขียน 12 หน้า หน้าละ 150 บรรทัด
และเมื่อแก้พฤติกรรมอย่างการยืนยันก่อนลบ จะมีผลกับทุกหน้าพร้อมกัน

### 4.2 หน้าที่ต้องเขียนเฉพาะ (12 หน้า)

| หน้า | เหตุผลที่ใช้รูปแบบร่วมไม่ได้ |
|---|---|
| สถานที่ · ประเภทอุปกรณ์ | โครงสร้างต้นไม้หลายชั้น ต้องย่อ-ขยาย และย้ายกิ่ง |
| ตู้ Rack | มีหน้าแสดงผังตู้แบบกราฟิก |
| ตารางการมองเห็น · บทบาทและสิทธิ์ | ตารางกากบาท ไม่ใช่รายการ |
| Collector Agent | มีขั้นตอนสร้างและแสดง API Key ครั้งเดียว |
| ขอบเขต OU | มีปุ่มทดสอบการเชื่อมต่อจริง |
| งาน Sync | มีตัวเลือกเวลาและการสั่งรันทันที |
| ผู้ใช้ระบบ | มีรหัสผ่าน การล็อกบัญชี การบังคับเปลี่ยนรหัส |
| SMTP | มีปุ่มส่งอีเมลทดสอบ |
| ประวัติการ Sync · ประวัติการแจ้งเตือน | อ่านอย่างเดียว ไม่มีการแก้ไข |

## 5. กฎการลบข้อมูลหลัก — ผลโดยตรงจากการออกแบบฐานข้อมูล

ฐานข้อมูลทั้งระบบ **ไม่มี `ON DELETE CASCADE` แม้แต่จุดเดียว** โดยเจตนา
การลบข้อมูลหลักที่ถูกอ้างถึงจึงจะถูกฐานข้อมูลปฏิเสธเสมอ

**หน้าจอต้องไม่ปล่อยให้ผู้ใช้ไปเจอข้อความผิดพลาดของฐานข้อมูล**

```
┌─ ยืนยันการลบ ─────────────────────────────────────────────────┐
│                                                               │
│   ⛔  ลบ "ฝ่ายการเงิน" ไม่ได้                                  │
│                                                               │
│   แผนกนี้ถูกใช้งานอยู่                                          │
│       •  ทรัพย์สิน   84 รายการ      [ ดูรายการ ]               │
│       •  โฟลเดอร์    16 รายการ      [ ดูรายการ ]               │
│       •  ผู้ใช้ระบบ    3 คน          [ ดูรายการ ]               │
│                                                               │
│   หากไม่ต้องการใช้แผนกนี้แล้ว ให้ปิดใช้งานแทน                     │
│   ข้อมูลเดิมจะยังอยู่ครบ แต่จะไม่ปรากฏในช่องให้เลือกอีกต่อไป        │
│                                                               │
│                        [ ยกเลิก ]   [ ปิดใช้งานแทน ]           │
└───────────────────────────────────────────────────────────────┘
```

| กฎ | เหตุผล |
|---|---|
| นับจำนวนการอ้างอิง **ก่อน** แสดงปุ่มลบ | ผู้ใช้เห็นตั้งแต่ในตารางว่าลบได้หรือไม่ ไม่ต้องกดแล้วค่อยพบว่าลบไม่ได้ |
| ปุ่มลบเป็นสีเทาเมื่อมีการอ้างอิง | ป้องกันตั้งแต่ต้น ดีกว่าแจ้งเตือนทีหลัง |
| เสนอ "ปิดใช้งาน" เป็นทางออกเสมอ | ตอบสิ่งที่ผู้ใช้ต้องการจริง คือไม่อยากเห็นในช่องให้เลือก ไม่ใช่อยากทำลายประวัติ |
| ลิงก์ไปดูรายการที่อ้างถึง | ถ้าตั้งใจจะลบจริง ต้องรู้ว่าต้องไปย้ายอะไรก่อน |

> ข้อมูลที่ปิดใช้งานแล้วจะหายจากช่องให้เลือกทั้งหมด แต่ยังแสดงในข้อมูลเก่าและรายงานย้อนหลัง
> เพื่อไม่ให้รายงานปีที่แล้วเปลี่ยนความหมายเพราะมีคนปิดแผนกวันนี้

| แยก "แสดงบนหน้าจอ" ออกจาก "เก็บในฐานข้อมูล" ให้ชัด | เป็นคนละเรื่องกัน และผู้ใช้มักเข้าใจผิดว่าตั้ง 3 version แล้วข้อมูลเก่าถูกลบ |
| อธิบายข้อจำกัดของ SQL Server ตรง ๆ | ดีกว่าให้ผู้ใช้ตั้งค่าแล้วสงสัยภายหลังว่าทำไมตารางยังโตอยู่ |
| แสดงขนาดที่ใช้อยู่จริง | ทำให้ตัดสินใจเรื่องระยะเวลาเก็บได้จากตัวเลข ไม่ใช่การเดา |
| ระบุว่าบันทึกการตรวจสอบลบไม่ได้ | มี Trigger บังคับไว้ที่ฐานข้อมูล ถ้าไม่บอก ผู้ใช้จะพยายามหาปุ่มลบ |

## 11. ความปลอดภัยของหน้าตั้งค่าเอง

| มาตรการ | รายละเอียด |
|---|---|
| ทุกการเปลี่ยนแปลงถูกบันทึก | ใช้ประเภท `SETTING_CHANGE` ที่มีอยู่แล้วใน `audit_logs` เก็บค่าก่อนและหลัง |
| หน้าที่เข้าถึงได้เฉพาะ Administrator | ทุกหน้าในกลุ่ม การเชื่อมต่อ · ผู้ใช้และบทบาท · ระบบ |
| ยืนยันรหัสผ่านซ้ำ | ก่อนสร้าง API Key ใหม่ และก่อนแก้ตารางการมองเห็น |
| ไม่แสดงค่าลับซ้ำ | รหัสผ่าน SMTP และ API Key แสดงเป็นจุดเสมอหลังบันทึกแล้ว |
| จำกัดจำนวนครั้งการทดสอบ | ปุ่มทดสอบ OU และส่งอีเมลทดสอบ จำกัด 10 ครั้งต่อชั่วโมงต่อผู้ใช้ |

## 12. สรุป

| รายการ | จำนวน |
|---|---|
| กลุ่มการตั้งค่า | 8 |
| หน้าทั้งหมด | 24 |
| หน้าที่ใช้รูปแบบร่วม | 12 |
| หน้าที่ต้องเขียนเฉพาะ | 12 |
| หน้าอ่านอย่างเดียว | 2 |

**ประเด็นที่ถือเป็นหลักในการออกแบบชุดนี้**

1. **ไม่มีทางตัน** — ลบไม่ได้ต้องบอกว่าเพราะอะไรและเสนอทางออก ไม่ใช่ขึ้นข้อความผิดพลาด
2. **ทดสอบได้ก่อนใช้จริง** — OU และ SMTP ต้องกดทดสอบได้ ก่อนที่จะรู้ตัวว่าผิดตอนที่มันสำคัญ
3. **สถานะต้องเห็นโดยไม่ต้องหา** — Sync ล้มเหลวและ Agent ขาดการติดต่อ ขึ้นที่หน้าแรกของการตั้งค่า
4. **บอกความจริงเรื่องข้อจำกัด** — เช่น API Key ดูซ้ำไม่ได้ และ SQL Server ตัดประวัติตามเวลาเท่านั้น
